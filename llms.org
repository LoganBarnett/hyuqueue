This file is the canonical contributor and LLM guidelines document for
hyuqueue.  ~CLAUDE.md~ at the repo root is a symlink to this file — always
edit ~llms.org~, never the symlink.

* General code guidelines

These are instructions for LLMs to write code more to my liking.

** Documents

When authoring new content, make them ~org-mode~ files.

Use ~:exports code~ if you just want to show off the code, and don't want it to
actually run anything.

No file lists in documentation.

** Comments

*** Formatting and punctuation

Comments must be complete sentences, wrapped at ~80 columns~, with standard
punctuation.

*** Content

Only comment non-obvious intent, invariants, tradeoffs, or historical
constraints; no restating of control flow.

** Code

*** Initialisms

Use Pascal Initialisms (~Url~) instead of Preserved Initialisms (~URL~) when
_authoring_ new identifiers in camel case.

** Rust

*** Error Handling

Prefer semantic errors.  Do not just wrap or propagate a ~FileMissingError~ or
~FileWriteError~.  This information _might_ include what file was involved, but
it doesn't say what was happening.  Include something either about the error
itself (like ~ConfigFileMissingError~) or about the process in which the error
occurred (~ReportFileWriteError~).

In cases where you can be semantic with your approach to APIs, use ~thiserror~
to automatically map API errors of certain kinds to semantic errors.

Generally this means there will be little reuse of error variants, and that is
acceptable.  Do not swallow errors — let them propagate.

*** Code Structure

**** Files and modules

~main.rs~ should only ever be an orchestrator.  Create sibling files for
associated functionality and have ~main.rs~ delegate to them.

Delegate obvious concerns: ~config.rs~ for configuration, ~logging.rs~ for
logging initialization.  It is okay if these wind up being a single struct and
a single function.

Keep ~.rs~ files under ~src~ for executables and ~lib~ for libraries.

**** Chains, local variables, and tap

Local variables should be generally frowned upon unless Rust specifically
requires them (for scope/ownership reasons), or a value has multiple uses.

You can further avoid local variables by using the ~tap~ crate to do logging in
the middle of a call chain without breaking the chain.

Prefer functional combinators over explicit ~loop~ and early ~return~.  When
functions grow complicated, simplify by extracting smaller functions.

**** ~for~ loops are a smell

Reach for ~.iter().map().collect()~, ~.try_fold(...)~,
~.filter(...)~, etc., before reaching for ~for x in xs~.  The
combinators carry the intent in the operator names; the ~for~ loop
buries it in the body and forces the reader to reconstruct what's
happening from the control flow.  Use ~for~ only when the body
genuinely needs imperative control flow (early ~break~ with
side effects, multi-step mutation that doesn't compose, etc.).

**** ~for~ loops with ~.await~ inside them are essentially errors

A ~for x in xs { x.do_async().await; }~ runs serially when the
operations are almost always independent and could run concurrently.
Reach for ~futures::future::join_all~, ~tokio::task::JoinSet~,
~try_join_all~, or ~stream::iter(xs).then(|x| async { ... })~
instead.  The serial form costs latency proportional to the number
of items times the per-item await time, with no upside — fan-out is
almost always free at the call site.

The narrow exception is when iteration order matters and an item
genuinely cannot start before the prior item finishes.  In that
case the loop is fine but the comment should say so explicitly.

**** ~out~ arguments are a smell

A function signature like ~fn collect_things(out: &mut Vec<T>)~
that mutates an argument instead of returning a value is the C
idiom for "no return value channel."  Rust has return values.
Return ~Vec<T>~ (or whatever).  Callers can ~?~, chain, or assign;
they cannot do any of those things with a function that writes
through a borrow.

The exception is when the function legitimately appends to a
pre-existing collection across multiple call sites (e.g. accumulating
into a builder that has structural reasons to be passed by reference).
Even then, prefer returning the collection if the call sites are few.

*** Debugging

When lacking information during debugging, permanent additions to the logs (at
appropriate levels) are one of the best cures.

Create tests which exercise the problem you are running into.  Prefer mock
services with integration tests so we can test real behavior, over unit tests
which test contrived situations.

Tests and test scripts must exit with a proper error code.

*** Types as validation

Only use ~Option~ if the field is truly optional.  If a struct would be invalid
without a field set, do not use ~Option~.  Instead, make an intermediate type
that represents a candidate whose validity is not yet fully known.

For example, ~CliRaw~ can represent arguments as provided on the command line.
~ConfigFileRaw~ can represent the configuration file's state.  Meshing the two
together yields a ~Config~ that represents a completely valid configuration.

* hyuqueue-specific conventions

** Crate structure

| Crate   | Responsibility                                       |
|---------+------------------------------------------------------|
| lib     | Shared types (LogLevel, LogFormat, LlmClient trait)  |
| core    | Pure domain (Item, Event, Queue, Topic, Activity)    |
| store   | SQLite persistence (sqlx, migrations)                |
| server  | axum daemon, REST API, async workers                 |
| cli     | Thin HTTP client binary                              |
| tui     | ratatui client (iron mode)                           |

** Event sourcing

~events~ is the source of truth.  The ~items~ and ~topic_data~ tables are
materialized projections.  All state changes (create, ack, refile, LLM
analysis, topic data updates) must be recorded as events.

** Worker patterns

Workers are long-running tokio tasks spawned at server startup.  Each polls
on a fixed interval with a batch size:

- Intake: 2s poll, batch 10.
- Review: 10s poll, batch 5.
- Outbound: 5s poll, batch 20, max 5 attempts.

Workers degrade gracefully on errors (log and continue).

** OIDC is optional

The server starts without authentication when OIDC fields are absent.
~AppState.oidc_client~ is ~Option<Arc<CoreClient>>~.  Auth handlers return
501 when OIDC is not configured.

* Verification

** Use the Nix development shell when available

If ~nix~ is available (~which nix~ succeeds), run all ~cargo~ commands inside
the Nix development shell rather than using whatever ~cargo~ is on the system
PATH:

#+begin_src sh :results none :exports code
nix develop --command cargo build --workspace
nix develop --command cargo test --workspace
#+end_src

This ensures the correct Rust toolchain and associated tools (such as
~rustfmt~) are in use.  The pre-commit hook requires ~rustfmt~ in PATH, so
~git commit~ must also go through the shell:

#+begin_src sh :results none :exports code
nix develop --command git commit -m "your message"
#+end_src

** Run all tests after changes

Run ~cargo test --workspace~ after making any change to verify nothing is
broken.
